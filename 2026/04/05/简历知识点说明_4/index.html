一、检索优化与生成融合 — 让 RAG 从“差不多”变成“很精准”

在基础 RAG 中，我们只是简单用向量检索找几个相关段落，然后拼给大模型。但这样往往效果不够好：可能召回不相关的内容、或者相关的内容排名靠后。检索优化 就是通过各种技巧提升召回的准确率（Precision）和召回率（Recall）。生成融合 则是让大模型更好地利用这些检索结果，避免 token 溢出等问题。

1. 混合检索 — BM25 + 稠密向量

检索方式 原理 优点 缺点
BM25 (稀疏检索) 基于关键词匹配，计算词频、逆文档频率 精确匹配关键词，速度快，可解释性强 无法理解语义同义词（比如“苹果”和“iPhone”）
稠密向量检索 (如 BGE) 将问题和文档映射到语义空间，计算相似度 能捕捉同义词、上下文语义 对罕见词或领域专有名词效果差

混合检索：同时使用两种方法，然后合并结果（如取并集、加权求和、或分别取 Top-K 再融合）。
效果：既能找到精确关键词匹配的文档，又能找到语义相似但无相同关键词的文档。

简单实现思路：

python

假设你已经有了 BM25 检索器和向量检索器

bm25_results = bm25_retriever.get_relevant_documents(query, top_k=5)
vector_results = vector_retriever.similarity_search(query, k=5)

合并去重，可以按分数加权排序

all_docs = {doc.page_content: doc for doc in bm25_results + vector_results}

然后按某种分数（如 BM25 分数 + 向量分数 * weight）排序

2. 重排序 (Rerank) — 精挑细选

问题：初检索（BM25 或向量）可能召回 10 个文档，但其中只有 3 个真正相关。
解决方案：用更强大但计算成本更高的 交叉编码器 对召回的文档重新打分，选出最相关的 Top-K。

交叉编码器 vs 双编码器

类型 原理 速度 精度 适用场景
双编码器 (如 BGE) 问题和文档分别编码成向量，计算相似度 快，可预计算文档向量 中等 初检索
交叉编码器 (如 BGE-reranker) 将问题和文档拼接后一起输入模型，输出相关性分数 慢（每个 pair 都要计算） 高 重排序（对少量候选精排）

典型流程：

  1. 初检索召回 Top-50 个文档（快速）。

  2. 用交叉编码器对这 50 个文档逐一打分，重新排序，取出 Top-5。
    效果：Top-5 召回率可提升 10~20%（如你简历中提到的 15%）。

使用示例：

python

from sentence_transformers import CrossEncoder
model = CrossEncoder(‘BAAI/bge-reranker-base’)
pairs = [[query, doc] for doc in top_50_docs]
scores = model.predict(pairs)

按分数排序，取最高分的前5个

3. HyDE (假设文档嵌入) — 让查询更“丰满”

问题：用户查询通常很短（如“奖学金政策”），缺乏上下文，直接检索效果不佳。
HyDE 思路：先让 LLM 根据查询 生成一段假设的答案文档，然后用这个假设文档去检索（而不是用原始查询）。
原理：假设文档更接近真实相关文档的分布，能检索到更精准的内容。
注意：有风险（LLM 可能瞎编），但实验证明在很多场景有效。

4. Self-Query — 让 LLM 自己拆解查询

场景：用户问“去年发表的关于 LoRA 的论文有哪些？” — 这包含语义部分（LoRA）和元数据部分（去年发表）。
Self-Query：让 LLM 从用户查询中提取出 语义查询 和 元数据过滤条件（如日期、作者）。然后分别用于向量检索和数据库过滤。
实现：定义一个 schema（如 {query: str, year: int, author: str}），让 LLM 结构化输出。

5. 生成融合 — 动态构造 Prompt 与 token 溢出处理

动态构造 Prompt

  • 将检索到的上下文块拼接成一段文本，插入到系统 Prompt 中。

  • 需要注意：保留上下文块之间的分隔，指示模型优先使用这些信息。

Token 溢出问题

  • 原因：检索到的上下文太长，加上用户问题、历史对话、系统指令，超过了模型的上下文长度（如 4k、8k）。

  • 解决方案：

    • 截断：按顺序截断，优先保留最相关的块（根据重排序分数）。

    • 压缩：使用 LLMLingua 等工具对上下文进行摘要或压缩，保留关键信息。

    • 滑动窗口：分多次处理，每次只送一部分上下文，最后合并结果（复杂）。

记忆口诀

混合检索 BM25+向量，关键词语义两不忘。
重排序用交叉编码器，精度提升靠精排。
HyDE 生成假设文档，Self-Query 拆解过滤。
生成环节防溢出，截断压缩滑动窗。

二、智能体（Agent）核心技术 — ReAct 与 Function Calling

Agent 的核心是让大模型 自主决策：思考需要做什么，然后调用工具执行，观察结果，再继续思考… 直到完成任务。

1. ReAct 模式 — 思考→行动→观察 的循环

ReAct = Reasoning + Acting。
每轮循环包含三步：

步骤 内容 示例
Thought 模型思考当前需要做什么 “用户问天气，我需要先获取城市，然后调用天气 API。”
Action 决定调用哪个工具，传入什么参数 get_weather(city="北京")
Observation 工具返回的结果 “北京今天晴天 25°C”

然后将 Thought + Action + Observation 作为新的对话历史，再交给模型，直到模型认为任务完成，输出 Final Answer。

手写 ReAct 循环的伪代码：

python

history = []
while not finished:
prompt = build_prompt(history) # 包含系统指令、工具描述、历史
response = llm.generate(prompt)
if “Final Answer” in response:
return extract_answer(response)
else:
action = parse_action(response) # 提取工具名和参数
observation = execute_tool(action)
history.append((response, observation))

2. Function Calling — 标准化的工具调用格式

不同模型的 Function Calling 格式略有不同，但核心思想一致：模型输出一个 结构化的 JSON，指明要调用的工具名称和参数。

OpenAI 格式示例

用户问题：“北京天气怎么样？”
模型输出：

json

{
“name”: “get_weather”,
“arguments”: {
“city”: “北京”
}
}

工具定义（给模型的 schema）：

json

{
“type”: “function”,
“function”: {
“name”: “get_weather”,
“description”: “获取指定城市的天气”,
“parameters”: {
“type”: “object”,
“properties”: {
“city”: {“type”: “string”, “description”: “城市名”}
},
“required”: [“city”]
}
}
}

本地模型（Qwen、GLM-4）的格式

  • 通常模仿 OpenAI 格式，或使用自定义格式如 <tool_call>...</tool_call>。

  • 你需要阅读模型文档，按照要求构造 prompt。

3. 如何手写 ReAct 循环（不依赖 LangChain）

关键点：

  • 把工具的描述（名称、参数、用途）写入系统 Prompt。

  • 要求模型输出格式固定，例如：

    text

    Thought: …
    Action: get_weather{“city”: “北京”}

    或者 JSON 格式。

  • 解析模型的文本输出，提取 Action 和参数，执行函数，得到 Observation。

  • 将 Observation 追加到对话中，重复。

4. 微调提升工具调用准确率

你简历中提到“通过对 Qwen-7B 进行少量样本微调，使工具调用准确率达到 92%”。
怎么做：

  • 准备训练数据：每条数据包含用户问题、正确的工具调用 JSON。

  • 使用 SFT（监督微调）训练模型，让它学会输出标准格式。

  • 评估：在测试集上检查模型输出的 JSON 是否完全匹配预期工具和参数。

为什么有效：通用模型可能输出格式错误（比如多出标点、参数类型错误），微调后更稳定。

5. 记忆口诀

ReAct 循环三步走：思考、行动、观察后。
Function Calling 标准化，JSON 输出工具调。
手写循环不依赖，微调模型准头高。

三、对比总结

技术 核心目标 关键方法 典型指标
混合检索 同时利用关键词和语义 BM25 + 向量检索 召回率提升
重排序 对初检索结果精排 交叉编码器 Top-5 准确率提升 15%
HyDE 解决短查询问题 LLM 生成假设文档 实验验证
Self-Query 拆解语义+元数据 LLM 结构化输出 过滤效果
ReAct 自主决策循环 Thought-Action-Observation 任务完成率
Function Calling 标准化工具调用 JSON schema 调用准确率 92%

四、动手小实验

  1. 混合检索：用 rank_bm25 库实现 BM25，结合 FAISS 向量检索，对 100 条查询评估召回率。

  2. 重排序：下载 BAAI/bge-reranker-base，对初检索的 50 个文档重排，看 Top-5 是否更好。

  3. HyDE：用 GPT 生成假设文档，代替原始查询去检索，对比结果。

  4. 手写 ReAct：不用 LangChain，只用 OpenAI API，实现一个能调用 get_weather 的 Agent。

  5. Function Calling 微调：用 LLaMA-Factory 或 Axolotl 对 Qwen-7B 微调工具调用数据。
